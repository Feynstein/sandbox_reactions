# M0-D51 — the desktop scope's port lock handed on before the port closed

Box: win-laptop (Laser2025-20), 2026-10-18. Model and level: model=claude-opus-5-5 level=high (`rung_record.py now`, the
heading's rung: no mismatch).

## The holder, measured first (logs/M0-D51.holder.log)
Black-box, launch.py's code unread: `launch.py start game-offscreen --task M0-D51-probe`, then `launch.py stop`, with
`connect()` on 127.0.0.1:47811 and the recorded pid's liveness (OpenProcess/GetExitCodeProcess) polled every ~10 ms around
the stop, netstat + CIM for the LISTENING owner after it.
- The listener outlives « stopped »: idle +25 ms, +60 ms; load 22 (22 busy procs on 22 threads) +2,962 ms (the whole 3 s
  window), +6, +2, +13 ms. The recorded pid already reads exited every time; by the first netstat (~100 ms+) no LISTENING
  owner is left. No other process binds 47811. The holder is the stopped game's own socket, torn down after its exit code.
- `stop` itself ran 3.6–4.7 s idle, 7–29 s loaded, once « (needed SIGKILL) ».
- Each `/status` poll leaves a server-side TIME_WAIT on 47811 (22 a run); the next start was accepted with 70 present —
  TIME_WAIT is not « held » on win-laptop.
- Not measured: linux-pc's holder at its refusal (M0-V8) — owed on laserax-ai (`ss -ltnp 'sport = :47811'` at the refusal).

## Cause
tests/smoke.sh released the port lock at the case's exit, right after launch.py's « stopped »; the port closes later. With
flock (linux-pc) the waiter wakes the instant the lock goes, so the launcher case's `launch.py start` probed 47811 inside
that gap under load → « held by a process we did not start ». Not a launch.py defect: « stopped » reads the pid, the lock is
the runner's.

## Fix (tests/smoke.sh)
`_sr_port_closed <port>`: bounded 30 s, until 127.0.0.1:<port> binds as the game binds it (SO_REUSEADDR on POSIX, as Rust's
std; none on Windows). `_sr_release` (the lock's EXIT trap, both lock kinds) runs it on 47811 before unlocking (headless-boot
excepted: it never binds 47811); the decoy's hand-over runs it on 47812 before freeing the web lock; the window and launcher
paths check it before their GO (« port 47811 still takes connections 30 s after … » is a NO-GO). The lock's acquire moved
into `_sr_lock` (unchanged code) so `race` reuses it.

A first try probed with `connect()`: `race` went red with the fix in (the game's own bind failed, os error 10048) — the
lingerer never accepts, its backlog filled under the probe's polls, and Windows refused connects while the port was still
bound. A refused connect is not a free port; the probe binds.

## Reproduction (case `race`, plant `port-handover-early`)
`race`, under the lock throughout: a listener launch.py did not start holds 47811 for 10 s (fd 8 closed for it, so it never
holds the flock); the case waits for the port with `_sr_port_closed` — every hand-over's wait — then runs
`launch.py start <window route>` straight behind it, which must reach ready. The plant makes `_sr_port_closed` return 0 (the
lock handed on at « stopped », the old behaviour); planted, `race` reads the symptom verbatim: « game-offscreen: port 47811
held by a process we did not start - not reusing ».

A first design used two holders (a subshell holding and handing on, the case taking the lock behind it): its plant stayed
GREEN in the first red-arm — five arms contend for the box's lock, other arms' cases took it between the two holders, and
the case got it only after the 10 s listener had gone. Holding the lock throughout makes the gap certain.
