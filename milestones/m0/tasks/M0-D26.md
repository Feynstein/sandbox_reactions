# M0-D26 — the Sun-sized box's fixed cost per pass

Box: win-laptop (Laser2025-20), NVIDIA GeForce RTX 4080 Laptop GPU, Vulkan, on AC power. Tree: b1938a8 + lot 4 + M0-D25
+ this block. Ran on claude-opus-5-5, high (`rung_record.py now`). Raw output: `logs/M0-D26.log`. The Quadro RTX 4000's
figures are **owed on laserax-ai** (contract §6.6; flagged into M0-V5).

## What changed (3 code files, ~60 lines)
1. **wgpu's indirect-call validation off** — `sr_engine::gpu::instance_flags()` (the headless instance's and, through
   `sr-app`'s `wgpu_setup`, the app's): wgpu 30 keeps `InstanceFlags::VALIDATION_INDIRECT_CALL` even in release builds
   (`InstanceFlags::from_build_config`), which puts a hidden compute dispatch before every `dispatch_workgroups_indirect`
   to turn an over-limit size into a no-op. Seven indirect dispatches a step on sun_disk (P0's `box_cells`, `box_fit`;
   P2's `grav_gradient`; P8's two; P9's `dt_cells`) paid ~11–14 µs each. Every indirect size the step reads is bounded by
   the world (box tiles ≤ 256 an axis, 256-cell groups ≤ 2048²/256 = 16,384 < 65,535) — a compile-time assertion in
   gpu.rs holds it; `WGPU_VALIDATION_INDIRECT_CALL=1` turns the validation back on. No shader reads `num_workgroups` (the
   D3D12 caveat in wgpu's doc).
2. **One compute pass per step when its passes are not timed** — `Step::encode_step` lists each pass's dispatch lists
   as before, then records them pass by pass (each a compute pass with its two timestamps) only when the step's passes
   are GPU-timed (`Timer::times_passes`: GPU timestamps and the step still fits the query set); otherwise the whole step
   is one compute pass — the same dispatches in the same order, wgpu still putting a barrier before each dispatch that
   reads what an earlier one wrote. Timing off, wall-clock timing and a frame's untimed tail all take the single pass.
3. Docs: the module doc and `encode`'s in step/mod.rs, docs/agent/architecture.md (§ One step, the cost bullet, a new
   bullet on the flag).

**No result changed**: final and intermediate dumps (`--steps 1000 --dump-every 250`) of the before and after binaries
are byte-identical at steps 250, 500, 750 and 1000 on sun_disk and fill_world (`cmp`, logs/M0-D26.log).

## Levers measured and not built (why)
- **P2's dispatches sized by the box** (`SR_D26_P2=256x96`, sun_disk's box): P2 0.069 → 0.064 ms timed, ~5 µs. Needs
  P2's row and column counts written by `box_fit` into the box's indirect sizes, which a dump's `resume.box_args`
  carries (contract §0.5 [M0-T26]) — a format change for ~2 % of the step. Not built; the early-returning workgroups are
  cheap once the validation is off.
- **P0 recording nothing when no edit is pending**: P0 today is `box_gate` plus two gate-sized dispatches; tests raise
  the edit flag on the GPU (`box_edit_flag`, box.rs and latch.rs), so only the CPU's edit queue (§1.12's lot) can know to
  skip it. After this block P0 costs 0.0137 ms timed and ~3 dispatches' barriers untimed — for the edit lot to gate.
- **What is left**: one pass per step, sun_disk's GPU time is ~0.143 ms for ~14 dispatches, ≈ 10 µs each — the barrier
  between dependent dispatches on this card. The next lever is fusing dispatches (TW R8: "fusing kernels to fewer
  dispatches is the lever for small boxes"), e.g. P8's two per-cell kernels into one; it changes the dispatch lists the
  `floors` and `state` scopes grade, so it is a block of its own if lot 5's budget needs it.

## Findings measured, not acted on
- **The card's clocks move the Symptom's numbers**: the 200 / 2,200-step protocol runs 0.1–0.9 s, partly before the
  laptop GPU clocks up — sun_disk's "before" reads 0.257 ms timed in short runs, 0.175 after long ones; the wall
  differencing swung 0.28–0.67 ms on one binary. A V reading per-pass costs on win-laptop should warm the card first
  or difference long runs. Not a defect of the code; the Quadro's protocol is laserax-ai's (§6.6).
- **A timed step still pays the pass boundaries**: under GPU timestamps every timed step is recorded pass by pass
  (per_pass_ms needs it) — sun_disk 0.141 ms timed against 0.113 untimed at steady state. The game times every frame
  for c_step (§1.8.3), and a frame of ≤ ~170 steps is timed whole; flagged into M0-T84 (the frame loop), which turns
  timing on: time the step as one compute pass (two timestamps a step) when per-pass costs are not asked for.
- **Against TW's budget** (M0-V4's arithmetic, my reading): scenario C needs ≤ ~0.124–0.138 ms a step at the top rung —
  sun_disk's steady wall (0.113 ms) is now inside it on this card, its timed GPU span (0.141) at the edge, before hydro,
  heat and burning exist. The Quadro's figure decides (owed).
