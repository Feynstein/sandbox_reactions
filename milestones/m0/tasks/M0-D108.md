# M0-D108 — win-laptop's six red-arm timeouts: the arms queued inside their own timeouts

Box: win-laptop (Laser2025-20), RTX 4080 Laptop, Vulkan; 2026-10-30. Model and level: `rung_record.py now` →
model=claude-opus-5-5 level=high.

## Cause, measured (from the sweep's own logs, no re-run)
Neither of the block's two readings is a different cause: there is one cause, and it is reading (a).
- In a red-arm scratch copy (no `.git`), `tests/cargo.sh` makes `cargo` a wrapper that runs the whole command inside the
  shared target's lock (`redarm-target.lock`; on Git Bash, which has no `flock`, the `.lock.d` mkdir lock). `tests/gpu.sh`
  and `tests/cpu.sh` call `cargo test`, which builds **and runs** the tests, so the lock covers the test run as well as the build.
  A campaign's arms (verify.py `arm_workers`: up to `--jobs`, 8 here) therefore ran one after another, but verify.py starts
  every arm's `timeout_s` when the campaign starts.
- Each campaign's arms ended in a staircase, one arm's cost apart (logs/M0-V11-win.<scope>.redarm.log, `-- … exit=… · N s`):
  - dump: 162, 298, 426, 543, 680, 777, 895 s, then dump-sim-time-skip at 900.69 s, two `Compiling` lines in: it got the lock at ≈ 895 s.
  - observe_run: 223, 363, 515, 635, 769 s, then lone-sink-left-out at 900.28 s, inside its third case (it got the lock at
    ≈ 769 s), and until-never-met at 900.28 s with a 0-byte `.part` (it never held the lock).
  - calibrate_bisect: 281, 608, 632, 921, 933, 1256, 1587, 1993, 2201, 2492 s, then calibrate-progress-every-ignored at 2700.50 s inside a
    case, and calibrate-record-removed and calibrate-resume-any-mass at 2700.5 s, with 0-byte `.part` files.
- So the cause was not the GPU: only one arm ever ran on the laptop GPU at a time. The RTX 4090 reads them RED because its
  queue empties before the cap (campaigns of 288, 613 and 1,157 s). The RTX 5090's until-never-met ERROR at 904 s (M0-D100) fits the same queue.
- The docs already recorded it once: M0-D80 raised calibrate_bisect's timeout to 2,700 s because "its red-arm's arms queue on one build
  target, the wait inside each arm's timeout". It came back as plants were added.

## Fix (the lead: «arms_at_once key (Rec.)»)
- verify.py: a scope key `arms_at_once` (an integer ≥ 1) caps how many arms a campaign runs at once
  (`arm_workers`); anything else makes the scope NOT RUN. This is a toolkit local divergence: tasks/toolkit_local_diff.md item 9.
- verify.json: `"arms_at_once": 1` on the 65 scopes whose command is `bash tests/gpu.sh|cpu.sh|cargo.sh`. The arms already ran
  one at a time, so a campaign's wall time is about what it was. Each arm's timeout now covers only its own work, and each
  arm's command is unchanged, so every plant reads the same on every box.
- Selftest: `v_arms` (a 0 is NOT RUN), an `arm_workers` unit check, a serial-arms campaign `aa` and its mutant plant
  (the key ignored → the arms overlap); verify.json plant `tools-selftest-arms-at-once` (tools_selftest, case `verify`).
- docs/agent/testing.md: § Cargo scopes says the lock covers the test run, plus the key; calibrate_bisect's row records why
  the timeout is 2,700 s.

## Not changed, named
- calibrate_bisect's `timeout_s` stays at 2,700 s. With the arms serial, an arm's own cost here is ≤ ≈ 330 s (the staircase steps), and
  bisect-tolerance's was 2,492 − 2,201 ≈ 291 s. Lowering it is not this block's job.
- `boot` (`tests/smoke.sh`) builds through `sr_build_app`, which holds the lock for the build only and launches its own
  copy, so its arms really do run side by side. It has no key. Its timeout still includes the build queue (2 plants: harmless).
- With the key, a campaign's wall time on this box is roughly the sum of its arms: observe_run ≈ 17 min, dump ≈ 16 min,
  calibrate_bisect ≈ 50 min. All three are over ten minutes, so Verify 1 is the lead's.
