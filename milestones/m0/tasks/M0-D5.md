# M0-D5 — scratch_copy.sh's selftest fails one check on Windows (2026-10-08, win-laptop)

## Cause (measured — the first suspect, in the tool, not the selftest)
`copy` resolves the source with `cd && pwd -P` and the destination with `realpath -m`, then tests
`"$dest/" == "$src/"*`. In Git Bash the two resolutions disagree: with `TMPDIR=/c/Users/YOHANB~1/AppData/Local/Temp`,
`pwd -P` gives `/c/Users/YohanBelanger/…` (8.3 name expanded), `realpath -m` keeps `YOHANB~1`. Probed also: `pwd -P`
normalises letter case and the `/tmp` mount (`/tmp/x` → `/c/Users/YohanBelanger/AppData/Local/Temp/x`); `realpath -m`
does neither. So «inside the source» was never seen, `mkdir` + rsync ran into `src/inner`, and the check
(«NO-GO, nothing created») went red. A real guard hole on Windows, not only a fixture's: `scratch_copy.sh /tmp/x
/c/Users/…/Temp/x/inner` would have copied a tree into itself. Not the other suspect (the guard runs before `mkdir`).

## Fix (the tool's guard), one helper + one line
`canon <path>`: `realpath -m`, then `pwd -P` on the deepest existing folder, the missing tail appended — the dest
is resolved the way the source is. On linux-pc `realpath -m` already resolves symlinks of existing parts, so the
result is the same there. Edges probed: `/` → `/`, `/nonexistent/a/b` unchanged, a lower-cased short-name path →
the long, cased form. The selftest is unchanged.

Where it landed — the lead's answer (question tool, 2026-10-08): «Both, identical». `tools/pb/scratch_copy.sh` and
PLAYBOOK.md annex §A.7's `#### tools/pb/scratch_copy.sh` block, byte-identical (`cmp`: identical); the
`<!-- pb:file ... md5: -->` marker `de04c76b5215` → `02dd8f26fbf3` (old value reproduced from
`git show HEAD:tools/pb/scratch_copy.sh`). No other file carried the old md5.
