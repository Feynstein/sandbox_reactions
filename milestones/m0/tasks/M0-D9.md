# M0-D9 — red-arm's shared cargo target reused a planted build

Box: linux-pc (laserax-ai), 2026-10-09. Model/level: claude-opus-5-5, high (rung_record.py now).

## Measured cause
- Repro before the fix: `verify.py --redarm adapter` twice (M0-D9.repro1/2) — both clean arms NO-GO «5 failed», the plant never ran.
- In a fresh scratch copy (scratch_copy.sh), `crates/sr-engine/src/gpu.rs` keeps the tree's mtime (09:13:24); the shared
  target's sr-engine fingerprint was written at 09:14:03 by the plant arm. `cargo test --no-run` with
  `CARGO_LOG=cargo::core::compiler::fingerprint=info` compiled nothing and served `gpu-84aac530e0e30dd8` (the planted build).
- `touch` of the copy's `crates/**/*.rs` → `Compiling sr-engine` only, 10 passed, 3 s wall. Cause confirmed: cargo's
  mtime freshness + rsync-preserved mtimes + one target dir shared across copies (dep-info paths are package-relative,
  so copies at different paths share fingerprints).

## Fix (tests/cargo.sh, scratch-copy branch only)
A `cargo` shell function: takes `~/.cache/sandbox-reactions/redarm-target.lock` (`flock`; else a mkdir lock `….lock.d`
holding its PID, broken when that PID is gone), touches every file under `crates/ assets/ scenes/ .cargo/` and
`Cargo.toml Cargo.lock`, runs `command cargo "$@"` inside the lock. The lock is what makes it right when arms build in
parallel (several plants, jobs_cap 8): a touch-once-per-copy would let arm A build after arm B's touch and B reuse A's
build. The real tree (`.git` present) is untouched.

## Evidence (linux-pc)
- `--redarm adapter` × 3 (M0-D9.adapter1..3): clean GO 10/10, plant RED 5 failed, each run ≈ 5.8 s; the third log shows
  `Compiling sr-engine` per arm and no dependency compiled.
- `--redarm build` × 3 (M0-D9.build1..3): plant RED each time; 30.5 s, 1.8 s, 1.6 s (the first run built the wasm
  side's dependencies into the shared target after earlier clears; then cached).
- Direct check in a copy: `cargo build --workspace --release` → `Compiling sr-physics`, `Compiling sr-engine`, 0.28 s.
- Fallback lock (flock forced off): two concurrent builds both exit 0, each recompiles the 2 crates, lock dir removed;
  a stale `.lock.d` with a dead PID is broken (cargo --version returns).
- NOT PROVEN on win-laptop (Git Bash, possibly no flock — the mkdir path covers it; owed at the next V there).

## Notes
- The `build` scope's plant was never actually fooled: its planted wasm check fails (no artifact stored) and its native
  build is code-identical to the clean one. The adapter scope was the live case.
- A scope that calls `command cargo` or `~/.cargo/bin/cargo` bypasses the wrapper (docs/agent/testing.md § Cargo scopes).
