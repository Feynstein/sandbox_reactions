# M0-D15 — the launcher case's `start.bat` « not recognised » on win-laptop

Box: win-laptop (Laser2025-20), 2026-10-09 · model=claude-opus-5-5 level=high (rung_record).

## Cause (measured, logs/M0-D15.log)
- The Bash tool's environment carries `NoDefaultCurrentDirectoryInExePath=1`. With it set, cmd.exe does not search the
  current directory when it looks up a bare command name, so `cmd //c "start.bat game-offscreen"` reads « 'start.bat'
  n'est pas reconnu… » even though cmd's cwd is the repo root (`cmd //c cd` → `C:\workspace\sandbox_reactions`;
  `if exist start.bat` → yes; `where start.bat` finds it).
- A/B/C on a throwaway echo-only `probe.bat` in the scratchpad: A, the variable set, bare name → the same « not
  recognised », rc 1; B, the variable unset, bare name → runs, rc 0; C, the variable set, `.\probe.bat` → runs, rc 0.
- Git Bash's quoting and path conversion are not at fault: `%CMDCMDLINE%` reads `cmd.exe /c "…"` as intended.

## Fix
- tests/smoke.sh, `run_launcher`'s MINGW branch: `cmd //c ".\\start.bat $service"`, so cmd reads `.\start.bat`. It
  works whether or not the variable is set. No expectation was loosened.

## The plant (the lead's yes, 2026-10-09: « Extend the plant (Recommended) »)
- The first `--redarm desktop` after the fix read NO-GO: `launcher-no-stop` patched start.sh only, which win-laptop
  never runs, so it stayed GO there (unfailable on this box). The launcher case was red on win-laptop until this fix,
  so nothing had shown this before.
- tests/plants/launcher-no-stop.patch now also removes start.bat's `launch.py stop` line, so one diff covers both
  launchers. Its hunk is LF, matching the patch's `eol=lf`. On a CRLF start.bat, `git apply` and GNU `patch -p1`
  both apply it cleanly (scratch dry run); `git apply` keeps CRLF and `patch` writes LF, and cmd runs either.
