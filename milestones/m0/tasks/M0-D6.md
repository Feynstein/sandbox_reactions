# M0-D6 — status_page's selftest flakes on Windows: the 413 arm dies with WinError 10053 (2026-10-08, win-laptop)

## Cause (measured — the suspect named in the block, in the tool's server, not the selftest)
`do_POST` refuses a body over `MAX_BODY` (64 KiB) by replying 413 with `close_connection = True` and never reads the
body. Closing a socket with unread bytes in its receive buffer sends a reset; on Windows the client's pending
`recv` then fails `ConnectionAbortedError: [WinError 10053]` before it reads the 413. Two faces in the selftest,
one cause: the abort inside `OPENER.open` → `fetch` returns 0 → the 403/400/400/413 check reads red (logs/M0-TE-win-r42);
the abort inside `e.read()` of the `HTTPError` branch escapes `fetch` → «suite raised ConnectionAbortedError»
(logs/M0-TE-win-r3, 27 checks). Probe (scratchpad, the handler alone, 300 POSTs of a 65 548-byte form): **12/300
and 29/300 aborted** before the fix; the 403 and 404 arms (small bodies, also unread) **0/300** each — only the
over-size arm is exposed.

## Fix (the tool's server), one method + one call
`drain(n)`: read and drop the refused body before the 413 — at most 1 MiB (`16 * MAX_BODY`), 2 s socket timeout,
any `OSError` ends it; a malformed length (`n = -1`) reads nothing. The connection still closes after the 413.
A client that lies about a length over 1 MiB can still see a reset — bounded on purpose (no unbounded read). The
selftest is unchanged. Probe after: **0/300 aborted** (control on the old tool, same minute: 29/300).
