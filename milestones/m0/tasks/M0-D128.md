# M0-D128 — M0-D107's port-holding cases on linux-pc

Box: linux-pc (laserax-ai). Model and level: model=claude-opus-5-5 level=high (rung_record now, at launch). Raw probes: logs/M0-D128.log.

## What the three symptoms were, measured

### (a) `web[ready-held]`'s listener: Errno 98 from TIME-WAIT, not a lock gap
- The plan suspected the listener bound outside the port lock. It doesn't: check.sh takes the port lock (`take_port_lock`, flock on
  `${TMPDIR:-/tmp}/sr-web.lock`) before the listener, and every case also holds the tree's build lock through its smoke, so the cases were
  already serialized. V12's run 1 order bears it out: `no-webgpu` ended 11:42:25, `ready-held` began 11:42:25, `ready` at 11:42:41.
- The cause: `http.server` is HTTP/1.0 and closes each connection itself, so a smoke leaves **server-side TIME-WAIT sockets on 47840**
  for about 60 s (`ss -tan` after the baseline run: `TIME-WAIT 127.0.0.1:47840 127.0.0.1:41134`, two of them). On Linux, a bind
  without SO_REUSEADDR conflicts with them; launch.py's `http.server` sets SO_REUSEADDR and binds fine. Probe (a) in logs/M0-D128.log:
  a server on 47995, two GETs, stopped → `reuse 0 bind [Errno 98] Address already in use` · `reuse 1 bind OK`.
- So in V12's run the listener died, nobody held 47840, and launch.py rightly took it. The case then blamed launch.py.
- Win-laptop's Windows sockets don't refuse that bind, which is why M0-D107 went GO there.

### (b) `desktop[launcher]`'s decoy «died before ready, exit 1» in V12's red-arm: cause not measured
- The plan's suspicion (parallel arms sharing one decoy port) is refuted: V12's red-arm line reads «1 arm(s) at a time», and the
  log's arms do not overlap (arm 0 11:48:58–11:49:21, arm 1 from 11:49:21).
- The decoy's own log was inside the arm's scratch copy and went with it. Not reproduced: a `--redarm desktop` today
  (M0-D128-repro, before any change) had its clean arm GO. Neither did foreign servers on 47841–47842 (as V12's leaks) beside the
  launcher case in the tree (probe (b), GO). `http.server` with a missing `--directory` stays up (probed), so exit 1 is a bind failure
  on the port launch.py handed it. What held that port is unknown.
- The case now prints the server log's last 20 lines when the decoy (or check.sh's server) fails to start, so the next sighting
  carries its cause.

### (c) the two leaked servers: ready-held's, from a records race in launch.py
- They were not decoys. `python3 -m http.server 47841` started 10:37:37 = M0-D119's `web[ready-held]` («the server on 47841»,
  logs/M0-D119.web.log); `… 47842` started 10:45:26 = M0-D120's ready-held, «the server on 47842» (47841 still held by the first).
  Both claims ran `desktop` beside `web`.
- Probe (c): `launch.py start web` + `launch.py start headless-boot` at once, six rounds. The records file
  (tools/pb/.launch.pid.json) kept one entry in 3 rounds, both in 2, and was torn JSON once («Extra data»). Three servers survived
  their stops; I stopped them by pid (my own probe's).
- Root cause in launch.py (an unlocked read-modify-write of the records file) is outside this block's files and is the toolkit's →
  filed as **M0-D131**. The two V12-era leaks were already gone when this task began (`ss -ltnp` empty).

## What changed
- tests/web/check.sh:
  - `ready-held`'s listener sets SO_REUSEADDR on POSIX (none on Windows, where it would let a bind steal a listening port) and
    writes `.up` or `.err`. A bind it cannot make is now «the case's own foreign listener could not bind …», never a blame on launch.py.
  - Every serving case stops its server itself after the smoke, and `port_free` (a bind as http.server binds, 30 s) must pass.
    Otherwise it is a NO-GO naming the pid read from `launch.py status` right after the start, and the case kills it (`kill`, or
    `taskkill //F` on Git Bash).
  - A failed start prints the server log's tail.
- tests/smoke.sh (`launcher`): the decoy gets the same: its pid read after start, `_sr_decoy_down` before the GO with the port check,
  a NO-GO + kill when it outlives its stop, and the log's tail on a failed start.
- Plants: `web-stop-lost` (web) and `launcher-decoy-left` (desktop) — the stop aimed at another service, as a lost record leaves it;
  `web-port-ignored` re-cut (its trailing context moved). All registered in verify.json.
